## 1. Executive Summary & Epistemic Taxonomy

This matrix establishes the definitive boundary between frontend presentation and authoritative backend responsibilities for every major capability in the Foundation v2 platform.

### Authoritative Backend Availability Taxonomy
To maintain strict architectural governance and eliminate wishful thinking, the `Current Backend Availability` column uses exclusively the following five standardized classifications:
- **`ACCEPTED_V2`**: Built, verified, and merged into Foundation v2 architecture (e.g., B0 domain models, B1.1 OOXML preflight within its qualified scope).
- **`LEGACY_PROTOTYPE`**: Historical or un-governed code exists in the repository (e.g., prototype upload scripts, direct PATCH endpoints, GTPS mapping). **Its presence does NOT constitute accepted Foundation v2 architecture.**
- **`PROVISIONAL`**: Technology spike completed behind an experimental harness (e.g., B1.2A Docling qualification spike), but not qualified or integrated into production.
- **`NOT_IMPLEMENTED`**: Capability is formally architected and contracted, but no production backend service or concrete persistence adapter exists in active code.
- **`UNKNOWN / REQUIRES_CONFIRMATION`**: Current source evidence is ambiguous or incomplete; requires explicit confirmation from backend leads.

**Key Rule:** Prototype or legacy availability must never be conflated with accepted Foundation v2 capability.

## 4. Current Phase Synthesis & Governance Rules

1. **Phase Reality (U0 / B1):**
   - Live backend currently supports B0 (frozen domain contracts, state machines, invariant engine, hash calculation mechanics) and B1.1 (OOXML Transitional package preflight assessment).
   - Concrete external persistence adapters, production Docling perception, native locators, controlled replay, execution, independent validation, and extraction endpoints are **NOT_IMPLEMENTED** in backend code.
   - Historical upload scripts, direct PATCH endpoints, and GTPS actions in the repository are **LEGACY_PROTOTYPE** artifacts and must not be treated as v2 architectural availability.
2. **Mocking Protocol:**
   - Where capabilities are marked `Mock Allowed? = YES`, U0 will use typed mock fixtures conforming strictly to `docs/contracts/foundation.openapi.yaml`.
   - The UI must display the global `SIMULATED BACKEND` banner whenever mock fixtures are active.
3. **Hard Governance Stops:**
   - Under no circumstances will the frontend claim native-fidelity extraction or successful replay execution until the backend qualification gates in `docs/CURRENT_BASELINE.md` are formally closed with recorded evidence.
