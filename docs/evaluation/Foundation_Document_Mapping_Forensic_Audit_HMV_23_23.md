## 1. Table Count Reconciliation

Before implementing code changes, the apparent discrepancy between the XML tag inventory and Foundation perception counts was audited:

- **Raw Word XML Tag Count**: **3,886 physical `<w:tc>` elements** inside `word/document.xml`.
- **Foundation Perception Element Count**: **4,231 table cell elements**.
- **Reconciliation Finding**: In Word OOXML, horizontal table cell merges are structured via `<w:gridSpan w:val="N"/>` within a single `<w:tc>` element.
  - Across the 22 tables in this document, `w:gridSpan` adds extra logical column coordinates:
    - Table 5: 3 extra grid columns
    - Table 9: 1 extra grid column
    - Table 15: 14 extra grid columns
    - Table 17: 4 extra grid columns
    - Table 21: 323 extra grid columns
  - **Sum of Grid Span Expansions**: $3 + 1 + 14 + 4 + 323 = \mathbf{345}$ extra logical grid coordinates.
  - **Total 2D Logical Coordinate Space**: $3,886 + 345 = \mathbf{4,231}$ cells.
- **Architectural Conclusion**: This is **100% intentional and correct**. `python-docx`'s `row.cells` returns the cell reference at each 2D grid position $(r, c)$, matching the frontend's `docxAnchorMapping.ts::buildLogicalGrid` which maps $(r, c)$ coordinates to merged `<td colSpan=N>` DOM nodes.

### Root Causes Identified:
1. **[P0-A] Table Cell Tracked-Change Text Omission**: `parser.py` called `cell.text` directly, dropping all `<w:ins>` runs in table cells (3,883 cells extracted with empty string).
2. **[P0-B] Table Hash Identity Bridge Failure**: `anchor_builder.py::build_table_hash` computed table hashes from `cell.text`, causing table headers to produce empty (`'e3b0c442'`) or truncated hashes that failed to match the rendered DOM tables in the browser (accounting for 3,709 cell failures).
3. **[P2] EMF Vector Image Representation Mismatch**: 17 images stored as `.emf` Windows Enhanced Metafiles had their raw bytes rasterized to canvas/PNG in `docx-preview`, failing exact base64 byte matching.
4. **[P3] SmartArt / Canvas Drawing Identity Stamping**: 2 canvas containers lacked `data-drawing-id` on nested inner canvas elements.

## 3. Remediation Implementation (Fixes A, B, C, D)

### A. Table Fix: Tracked-Change-Aware Cell Extraction (`parser.py`)
- Centralized canonical text extraction in `foundation/perception/parser.py` via `extract_paragraph_visible_text(p_elem)` and `extract_cell_visible_text(cell)`.
- Traverses `<w:r>`, `<w:ins>`, `<w:hyperlink>`, and `<w:sdt>` in document order while strictly excluding `<w:del>` (deleted text) and field instruction codes (`<w:instrText>`).
- Replaced `_base_block("table_cell", text=cell.text)` with `_base_block("table_cell", text=cell_text)`.

### B. Table Hash Fix: Canonical Header Hash Parity (`anchor_builder.py`)
- Updated `build_table_hash(table)` in `foundation/perception/anchor_builder.py` to use `extract_cell_visible_text(cell)[0].strip()`.
- Guaranteed that SHA-256 table fingerprints generated by backend Python match the pre-layout DOM header fingerprints generated by `docxAnchorMapping.ts::computeHeaderHash` across all document revisions.

### C. EMF Image Fix: Authoritative `drawing_id` Bridge (`docxAnchorMapping.ts`)
- In `frontend/src/components/document/rendering/docxAnchorMapping.ts::mapImages`:
  - First queries `container.querySelector('[data-drawing-id="..."]')` matching `anchor.drawing_id` (the OOXML `wp:docPr @id`).
  - Falls back to raw byte matching via `fetchMediaBytes` for bitmap images (JPEG/PNG).

### D. Drawing Container Stamping (`DocxRenderer.tsx`)
- In `DocxRenderer.tsx`, updated `onElementRendered` to stamp `data-drawing-id` on any rendered container with `elem.foundationDrawingId != null`, regardless of tag name.
